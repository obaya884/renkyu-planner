## 1. 背景

オーナーは有休の計画をスプレッドシートで回している。シートがやっていることは 3 つある。

1. 残数の管理。支給日数（14 日、毎年 5 月 1 日付与）から、消化済み・予定・未消化を出す
2. 有休日程の記録。日付・消化量・予定の名前・消化済みかどうかを 1 行ずつ手で入れる
3. 有休候補の提案。祝日を曜日で分け、火曜と木曜の祝日には「飛び石埋め 4 連休」を、祝日のない月には「どこかの週を 3 連休にする」を出す

このやり方はオーナーには役立っているが、シートのままではほかの人が使えない。

- 付与日・日数・年の区切りが数式に埋まっていて、条件の違う人は数式を書き換えることになる
- 時間単位の休みは自分で日数（2 時間なら 0.25 日）に計算してから入れている
- 祝日だけで計算するので、年末年始や夏季休暇のような会社の休みが連休に数えられない
- 候補の規則が 2 種類だけで、「四半期に 1 度の長めの休暇」のような計画は出せない
- 日付の年を打ち間違えても気づけない

一方、世の中のサービスは「連休を見つけるもの」と「有給を記録するもの」に分かれていて、両方をつないだものは見つからなかった（§1.1）。

### 1.1 競合と差別化

2026-11-15 に、各サイトの説明と紹介記事から読み取った内容。実際に操作しての確認はしていない。

| サービス | 型 | できること | できないこと |
|---|---|---|---|
| 連休メーカー（darashi） | 見つける | 1 日休むと連休になる平日を 2026・2027 年の一覧で出す | 入力なし。会社の休日、2 日以上の休み、記録 |
| 連休シミュレーター（ベストカレンダー） | 見つける | 有給 0〜5 日を選ぶと GW・お盆・シルバーウィーク・年末年始の取り方を出す。2025〜2029 年。カレンダー購読と SNS 共有 | 会社の休みは年末年始 12/29〜1/3、お盆 8/12〜16 に固定。4 つの時期以外、残数、保存 |
| Japan Holiday Calendar（luft） | 見つける | 連休の前後に有給を取ると最大何連休になるかを年ごとに出す | 会社の休業日は反映されない。残数、保存 |
| Stretch My Time Off | 見つける | 国と有給日数を入れると、連休が最大になる取得日を自動で計算する。日本の祝日に対応 | 会社の休日と記録は紹介記事に記載なし |
| 有給休暇プランナー（Android） | 記録する | 残日数の計算、半日・時間単位、休日出勤と代休、通知 | 連休の提案は記載なし。Android のみ |
| 休み記録（iOS） | 記録する | 残日数の管理、特別休暇の記録、登録不要 | 連休の提案は見つからない。iOS のみ |

連休プランナーの違いは次の 4 つで、機能の要否で迷ったらこの 4 つを強めるほうを選ぶ。

1. **自分の会社の休みで計算する。** 競合は土日祝だけか、年末年始とお盆を固定の日付で数える。連休プランナーは会社の休日と特別休暇を利用者が入れる
2. **1 年を通して計画する。** 競合は 4 つの大型連休か、1 日休みの飛び石だけを見る。連休プランナーは四半期ごとに長めの休暇があるかを見せる
3. **見つけた候補が記録につながる。** 候補を日程に入れると持ち分が減り、未割り当ての日数が残る。「連休を作る」と「余らせない」を 1 つの画面で追える
4. **どの端末でも登録なしで使える。** 記録する型の競合は Android か iOS のどちらかに限られる

競合に負けている点は、対象の年（確定として扱うのは来年末まで）、自動の最適化、カレンダー購読・SNS 共有・通知。このうちカレンダーへの書き出しだけを MVP に入れる（F-506）。残りは §7 に置く。

## 2. 目的

有休と祝日と会社の休みを組み合わせて、連休を上手く作れるようにする。使った人には次の 3 つが起きる。

1. **連休が上手く作れる。** どこを休むと何連休になるかが、自分の条件で分かる
2. **四半期に 1 度くらい、長めの休暇が作れる。** 有休と祝日で 5 連休以上を、1 年に偏りなく置ける
3. **付与された有休を余らせない。** まだ割り当てていない日数がいつも見えている

### 2.1 成功基準

MVP の成功は次の 2 つで判断する（Claude の案。§11 U-2）。

1. **オーナーがスプレッドシートをやめ、連休プランナーだけで有休を計画・記録している**
2. **初めて開いた人が何も入力せずにこれからの候補を見られ、付与日と日数を入れるだけで自分の残りが出る**

MVP の先（アカウント機能など）へ進むかどうかは、利用の伸びを見て決める。伸びを何で測るかは未決（§11 U-3）。

## 3. 対象ユーザーと利用シーン

- **対象ユーザー**: 土日と祝日が休みで、有休を日単位・半日単位・時間単位で取る会社員。オーナー本人を最初の利用者とし、同じ条件のほかの人が自分の付与日・日数・会社の休みを入れて使えるようにする
- **対象外**: シフト勤務など土日以外が休みの人。1 年に何回も有休が付与される会社の人（§7）
- **利用シーン**:
  - **年の計画を立てる**: 有休が付与された時期や年の初めに開き、四半期ごとの候補を見て、休む日を決めて日程に入れる
  - **休みを取った・決めたときに記録する**: 結婚式や体調不良のように候補と関係なく決まった休みを足す。取り終えた日を取得済みにする
  - **残りを確かめる**: 残りの日数と、まだ割り当てていない日数を見て、次にどこで休むかを考える
  - **検索から来て候補だけ見る**: 「有給 連休」などで検索して来た人が、何も入力せずにこれからの候補を見る
- **利用環境**: スマホのブラウザを主とし、PC のブラウザでも同じ内容を使える（F-503）。インストールとログインは要らない

## 4. コンセプトと用語: 候補から選んで、1 年の休みを置いていく

画面の主役は「有休候補」である。利用者は候補を見て、気に入ったものを日程に入れる。入れるたびに持ち分が減り、四半期ごとの長めの休暇が埋まっていく。記録は候補を選んだ結果として残るものと位置づける。

### 4.1 用語

| 用語 | 意味 |
|---|---|
| 休みの日 | 働かなくてよい日。土曜・日曜・祝日・会社の休日 |
| 祝日 | 内閣府が公表する国民の祝日・休日（振替休日と国民の休日を含む） |
| 会社の休日 | 会社が決めていて全員が休む日。年末年始の休業、一斉に取る夏季休業など。利用者が登録する（F-103） |
| 休暇の種類 | 日数が決まっていて、休む日を利用者が選ぶもの。有休は最初から入っている。夏季休暇やリフレッシュ休暇のような特別休暇は利用者が足す（F-104） |
| 持ち分 | 休暇の種類ごとの、その 1 年に使える量。有休では、付与日数に前の年の残りを足して計算する。利用者が直すこともできる |
| 付与年 | 有休の付与日から次の付与日の前日までの 1 年。持ち分と記録はこの単位で数える。付与日（月日）と日付から自動で決まる（F-402） |
| 四半期 | 1〜3 月、4〜6 月、7〜9 月、10〜12 月。長めの休暇があるかを見るための区切りで、付与年とはずれていてよい（F-403） |
| 連休 | 休みの日と、1 日分の休暇を取った日が 3 日以上続いたもの。半日や時間単位の休みを取った日は連休に数えない |
| 長めの休暇 | 5 連休以上の連休 |
| 候補 | 「この平日を休むと何連休になる」という提案（F-201） |
| 日程 | 利用者が決めた休みの 1 件。日付、休暇の種類、量、予定の名前、取得済みかどうかを持つ（F-301） |
| 予定・取得済み | 日程の状態。これから取るものが予定、取り終えたものが取得済み |
| 残り | 持ち分から取得済みの量を引いたもの |
| 未割り当て | 残りから予定の量を引いたもの。まだ日を決めていない量 |
| 所定労働時間 | 1 日に働く時間。時間単位の休みを日数に直すのに使う（F-102） |

## 5. 重視する価値

機能の要否や優先度で迷ったとき、次の順で判断する（Claude の案をオーナーとのブレストの内容から起こした。番号は各文書からの参照用）。

| ID | 価値 | 意味 |
|---|---|---|
| C-1 | **候補が主役** | 開いたら、どこを休むと得かが最初に見える。記録や設定は候補を選ぶための脇役に置く |
| C-2 | **自分の条件で正しい** | 付与日・日数・会社の休み・特別休暇を入れると、その人の実際の連休と残りになる。祝日は公式のデータを使う |
| C-3 | **余らせない** | 未割り当ての日数と、長めの休暇がまだない四半期が、いつも目に入る |
| C-4 | **すぐ使える** | ログインもインストールも要らない。何も入力しなくても候補が見え、入力は使いながら足せる |
| C-5 | **預からない** | 休みの記録は利用者の端末に置き、運営側は受け取らない |

価値が衝突したら小さい番号を優先する。

## 6. 要求

優先度は Must（MVP に必ず入れる）、Should（MVP に入れたいが、後回しにしても公開できる）の 2 段階。挙動の細かい規則（計算の境界、並べ方の同点の扱い、文言）は要件定義書と画面定義書で決める。

### 6.1 条件の設定

| ID | 要求 | 優先度 |
|---|---|---|
| F-101 | 有休の付与日（月日）と、1 年に付与される日数を入れられる。その年に使える日数（持ち分）は、付与日数と前の年の残りから計算して出し、会社の数字と違うときは利用者が直せる。失効日の管理は持たない | Must |
| F-102 | 1 日の所定労働時間を、時間と分で入れられる（7 時間 45 分など）。初期値は 8 時間 | Must |
| F-103 | 会社の休日を、1 日または期間で登録できる。「毎年同じ月日」（年末年始の 12/30〜1/3 など）と「その年だけ」を選べる。登録した日は土日・祝日と同じ休みの日として連休の計算に入る | Must |
| F-104 | 休暇の種類を足せる。名前、日数、使える期間（任意。「7〜9 月」のような開始日と終了日）を入れる。有休は最初から入っていて消せない。足した休暇の持ち分は有休の付与年と同じ区切りで数え、毎年同じ日数が付くものとして扱う | Must |
| F-105 | 週の休みは土曜と日曜に固定し、設定項目にしない | Must |
| F-106 | 何も設定していない状態でも使える。そのときは、今の四半期から 4 つの四半期分（F-508）の候補を、土日と祝日だけで計算して見せる。持ち分と残りは出さず、付与日と日数の入力を促す（C-4） | Must |
| F-107 | 設定はいつでも変えられ、変えると候補・持ち分・四半期の表示がその場で計算し直される | Must |
| F-108 | 月カレンダーの週の始まりを、月曜か日曜から選べる。初期値は月曜 | Must |

### 6.2 候補

| ID | 要求 | 優先度 |
|---|---|---|
| F-201 | 休暇を 1〜3 日使うと、土日だけでは作れない長さの連休になる組み合わせを、主な画面に出す期間（F-508）についてすべて計算して候補にする。「土日だけでは作れない長さ」とは、休暇 k 日に対して連休が k+3 日以上になること（休暇 1 日なら 4 連休以上）。シートの「飛び石埋め」はこの結果の 1 つとして出る | Must |
| F-202 | 候補には、休む日と曜日、連休の期間（開始日〜終了日）と日数、使う休暇の日数を出す | Must |
| F-203 | 候補は四半期ごとに分け、休暇 1 日あたりの連休日数が多い順に並べる。同じ休みのかたまりを核にする候補（1 日休んで 4 連休、2 日休んで 5 連休など）は、ばらばらに散らさずまとめて見せる | Must |
| F-204 | 5 連休以上になる候補に「長め」の印を付ける | Must |
| F-205 | 平日の祝日も会社の休日もない月には、「どこかの週の金曜か月曜を休んで 3 連休にする」を、日付を決めない候補として出す。F-201 の長さの条件の例外とする。日程に入れるときは、その月の金曜と月曜から利用者が日を選ぶ | Must |
| F-206 | 候補の「日程に入れる」を押すと、その候補の休む日が予定として日程に入り、未割り当てが減る。入れるときに、どの休暇の種類から引くかを選ぶ（種類が有休だけなら選ばせない） | Must |
| F-207 | 日程に入っている 1 日分の休みは休みの日とみなし、日程が変わるたびに候補を計算し直す（金曜を予定に入れたあと、月曜を休めば 4 連休になるなら、それを候補に出す）。すでに日程に入っている日を休む日に含む候補は出さない。その日が作る連休は日程の側に出す（F-304） | Must |
| F-208 | 使える期間が決まっている休暇の種類に残りがあれば、その期間の候補では、有休より先にその休暇を充てる案を出す | Should |
| F-209 | 付与年の区切りをまたぐ連休も候補に出す。次の付与日以降の日は次の付与年の持ち分から引き、そのことが分かるように出す | Must |
| F-210 | 祝日が公表されていない先の期間（§6.6）の候補には「祝日が未確定」と出す | Must |
| F-211 | 未割り当てが足りない候補も隠さずに出し、足りないことが分かるようにする | Should |

### 6.3 日程と記録

| ID | 要求 | 優先度 |
|---|---|---|
| F-301 | 日程 1 件は、日付、休暇の種類、量、予定の名前（任意）、取得済みかどうかを持つ。量は「1 日」「半日」「何時間何分」で入れる。半日は所定労働時間の半分として数える | Must |
| F-302 | 候補にない日（結婚式、体調不良など）を、日程に直接足せる | Must |
| F-303 | 日程を編集・削除でき、予定を取得済みに切り替えられる | Must |
| F-304 | 日程には、その日が作る連休の期間と日数を出す。5 連休以上なら「長め」の印を付ける | Must |
| F-305 | 日付を過ぎた予定は、自動では取得済みにしない。利用者が切り替えるまで、過ぎていることが分かるように出す | Should |
| F-306 | 同じ日に、合計が 1 日を超える量を入れようとしたら知らせる | Should |

### 6.4 持ち分と四半期

| ID | 要求 | 優先度 |
|---|---|---|
| F-401 | 休暇の種類ごとに、残り・予定の量・未割り当てをいつも見えるところに出す。量は「9 日と 2 時間」のように日と時間（端数があれば分）で出し、小数にしない | Must |
| F-402 | 1 年は有休の付与日から数える（付与年）。持ち分・残り・未割り当ては付与年の単位で計算する。付与年は付与日（月日）と日付から自動で決まり、利用者が切り替える操作は要らない。日程は、その日付が入る付与年の持ち分から引く | Must |
| F-403 | 四半期（1〜3 月、4〜6 月、7〜9 月、10〜12 月）ごとに、日程の中に 5 連休以上があるかどうかを出す。あればその期間と日数を、なければ「まだない」を出す | Must |
| F-404 | 年 10 日以上の有休が付与される付与年で、有休の取得が 5 日に届いていないとき、あと何日かが目に入るように出す。付与年の終わりが近づいたら、警告として出す。数えるのは 1 日分と半日の休みで、時間単位の休みは数えない（労働基準法が会社に課す、年 5 日を取らせる義務に合わせる） | Must |
| F-405 | 付与日数と持ち分は付与年ごとに持つ。付与日数は、入れていない年には前の年の値を使う。持ち分は、付与日数に前の付与年の未割り当てを足して計算する。始まった付与年の持ち分は、利用者が直せる。過ぎた付与年の記録は見返せる | Must |
| F-407 | 新しい付与年が始まったら、その年の付与日数と持ち分を確かめるよう、目に入る所で知らせる。確かめたら消える | Should |

### 6.6 祝日データ

| ID | 要求 | 優先度 |
|---|---|---|

## 7. スコープ外

やらないと決めたもの。将来の候補は「候補」と明記する。

| 項目 | 扱い | 理由 |
|---|---|---|
| アカウント、端末をまたぐ同期 | **候補** | MVP は端末保存で出す。利用が伸びたら、アカウント機能と、端末にある記録の引き継ぎを検討する（オーナー決定） |
| 年間の案を自動で組む（残りをおまかせで埋める） | **候補** | MVP は候補を並べて自分で選ぶ。同じ候補の計算の上に足せる |
| 土日以外が休みの勤務（シフト勤務、週休 3 日など） | 対象外 | 対象ユーザーを土日祝休みの会社員に絞る（§3） |
| 1 年に何回も有休が付与される会社 | 対象外 | 付与年を 1 つの持ち分として数える前提が崩れる |
| 有休の失効日の管理、時効の計算 | 対象外 | 持ち分は付与日数と前の年の残りから計算し、違うときは利用者が直す（F-101）。繰り越しは前の年の付与日数までとする（要件定義書 R-13） |
| 慶弔休暇など、出来事が起きてから日数が決まる休暇の自動計算 | 対象外 | 取った日を会社の休日として手で入れれば、連休の計算には反映される |
| 時間単位の有休の年間上限、半休の回数制限など会社ごとの細かい規則 | 対象外 | 会社ごとの差が大きく、MVP では扱いきれない |
| 休日出勤と代休の管理 | 対象外 | 記録する型の競合の領分。連休を作る用途から外れる |
| カレンダーの購読（日程の変更に自動で追従）、通知 | **候補** | サーバーが要る。MVP は一度きりの書き出し（F-506）で代える |
| SNS 共有 | **候補** | 個人の休みの記録を共有する形を決めていない |
| 祝日が未確定の年の予測（春分・秋分の計算など） | 対象外 | 公式のデータだけを確定として扱う（C-2） |
| 日本以外の祝日 | 対象外 | 対象は日本の会社員 |
| ネイティブアプリ | 対象外 | ブラウザで登録なしに使えることが違いの 1 つ（§1.1） |
| 勤怠システムや会社の申請との連携 | 対象外 | 個人が自分で使う道具に留める |

## 8. プラットフォームと技術方針

### 8.1 検討した作り方

| 案 | 内容 | 判断 |
|---|---|---|
| 静的サイト | サーバーも DB も持たず、ビルドしたファイルを配る。記録は端末に置く | **採用**。MVP は端末保存と決めたので、サーバーが要る場面がない。費用と運用がほぼかからない |
| Next.js を Vercel に置き、全ページをビルド時に生成する | サーバー側の処理を書かず、利用者には静的なページを届ける。アカウントを足すときは同じアプリに API と DB を足す | **採用**（上の静的サイトを作る手段として）。hitosuji で慣れていて、アカウント機能への道が最も短い。検索向けのページも足せる |
| Astro に React を載せる | 説明文と候補をビルド時に HTML にし、動く部分だけ React にする | 不採用。静的サイトとして最も素直で送るスクリプトも少ないが、連動する主な画面では軽さの利点が薄く、オーナーのリポジトリに実績がない |
| Vite にプリレンダリングを足す | bassdrill と同じ構成に、HTML を書き出す仕組みを足す | 不採用。プリレンダリングが標準の機能でなく、ページが増えるほど自作が増える |
| MVP から API と DB を持つ | 最初からサーバー側の処理を書く | 不採用。需要が見える前からサーバーの運用を抱えることになる |
| 祝日を自前のサーバーから配る | 外部の出所が止まっても影響を受けない | 不採用。祝日をビルド時に同梱すれば、配信の仕組みを持たずに同じ効果が得られる（F-601） |

祝日の出所は Holidays JP API（Google カレンダー由来、ビルドは年 1 回、メンテナ 1 人）と内閣府の CSV を比べ、内閣府の CSV に決めた（[決定ログ](./log_11_要求定義書.md) 2026-11-15）。

### 8.2 方針

- **ブラウザで動く Web アプリ**。スマホと PC から同じ URL で開ける
- **サーバー・DB・認証は持たない**（N-01）。静的なファイルとして配り、記録はブラウザの保存領域に置く
- **枠組みは Next.js**。Vercel に置き、全ページをビルド時に生成する。`output: 'export'` は使わない。MVP ではサーバー側の処理（API、サーバーで動く関数）を 1 つも書かない
- **言語は TypeScript、画面は React、スタイルは Tailwind CSS、テストは Vitest**。hitosuji・bassdrill と共通にする（Claude の判断）
- **最初に返す HTML に内容を入れる**（N-04）。説明文と設定なしの候補はビルド時に HTML になる。設定・日程・持ち分は、端末の記録を読んでからブラウザで描く
- **ホスティングは Vercel の無料枠**（N-06。Claude の判断）。祝日の定期取り込み（F-602）は GitHub Actions で回す
- **アカウントを足すときへの備え**は N-02 と N-03 の 2 点だけにし、それ以上の先回りはしない

## 9. 名称

- サービス名は **連休プランナー**、リポジトリ名は **renkyu-planner**
- ページの題は「連休プランナー｜有給管理もできる休暇計画サービス」（オーナー案）
- 検索で探される語は「有休」より「有給」が多いと見て、題と説明文では「有給」を使う。画面の中の表記をどちらにそろえるかは画面定義書で決める

## 10. 前提と制約

- 祝日は、内閣府が公表した範囲しか確定として扱えない。内閣府は翌年分を毎年 2 月ごろに公表するので、確定しているのは最長で来年末まで
- 記録は端末ごとに別になる。PC とスマホで同じ記録を見るには、書き出しと読み込み（F-505）を使う
- ブラウザの保存領域は、利用者がサイトのデータを消すと失われる。運営側に写しはない（C-5）
- 競合の機能（§1.1）は説明文から読み取ったもので、操作しての確認はしていない
